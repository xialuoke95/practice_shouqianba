# 数据转换与对齐脚本通用工程原则

这份文档记录我们希望长期复用的一类原则：当一个脚本负责把已有数据转换到另一个训练、评测、服务或审计系统时，应该如何组织逻辑、暴露控制面、记录结果、支持后续演进。

这些原则不绑定 Fireworks、ms-swift、某个 renderer 或某一种 JSONL schema。具体字段可以随项目变化，但工程要求应尽量稳定。

## 1. 核心语义和工程控制分离

脚本里要区分两类逻辑：

- 核心语义：决定数据含义如何被转换，例如角色、标签、权重、引用关系、媒体对象、边界语义等。
- 工程控制：决定脚本如何运行，例如抽样、跳过策略、调试开关、统计输出、路径管理、运行规模限制等。

核心语义应该尽量保持集中、清晰、可审阅。工程控制不应该散落在核心转换分支里，避免后续加一个调试功能就改变数据语义。

## 2. 转换能力要模块化、可组合、可关闭

每个转换能力都应该是相对独立的模块，而不是堆在一个大分支里。

好的模块应该具备：

- 明确输入和输出
- 明确影响的数据语义
- 可以单独打开或关闭
- 可以单独统计效果
- 可以单独测试

如果需要提供“某个模式”或“某个版本”的组合开关，也应该把它实现为若干模块的 preset，而不是把所有行为塞进一个不可拆解的布尔值。

## 3. 主流程只做编排，复杂逻辑下沉到命名函数

主流程应该让读者快速看懂数据处理顺序，而不是承载所有细节。

角色处理、媒体处理、引用关系处理、权重处理、边界处理等复杂逻辑，应该下沉到命名清楚的函数里。函数名本身应解释这段逻辑在做什么。


## 9. 参考脚本是基线，不是隐藏依赖

如果存在历史脚本、上游脚本或其他团队提供的脚本，应该把它作为 reference baseline 管理。

对 reference 的每个重要差异，都应能说明：

- 已迁移
- 有意改写
- 暂不适用
- 需要后续确认

不要让主脚本“看起来独立”，但实际正确性依赖某个没人再看的参考脚本。

## 10. 重构后必须重新验证

转换脚本重构后，不能只凭代码更清楚就认为完成。

至少要验证：

- 语法和基础运行
- 小样本 smoke
- 关键模式或 preset 是否仍可运行
- 产物行数和核心统计是否合理
- 已有验收脚本是否仍通过

如果重构改变了输出语义，必须明确说明；如果不应改变语义，应做对比验证。
